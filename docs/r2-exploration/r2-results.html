What R2 is

Meaning beats matching

The three roads disagree about what kind of problem this is. R1 says it is a database query: the customer states facts, each fact eliminates products, and you intersect sets until one item survives. R2 says it is a ranking problem: score every candidate by how well it explains what the customer said, sort, and take ten.

The difference is not cosmetic, and it shows up in exactly one place — what happens when a constraint is worded differently than the catalog words it. R1's set intersection returns nothing: one changed character and the match is gone. R2's scored overlap returns a smaller number. One fails off a cliff, the other down a slope.

The race

A cliff and a slope

The fair-control result is the one that matters. R1 scores exactly zero partly because it has no fallback: when its regex misses, it ships an empty list every turn of every session. That is a missing guard, not an architecture. So we added the guard — fall back to the popularity prior, the same one R2 uses — and re-ran. It recovers to 0.0273. The collapse survives the fix, which is what makes it a finding about filters rather than a bug report about one file.

What we got wrong

Three reversals worth keeping

Reversal 01 · the schedule

A prior matters most where the evidence stops discriminating

The first weight schedule decayed popularity from 1.0 to 0.32 as constraints accumulated — the intuitive move, since hard evidence ought to take over from a prior. Raising it back to 2.5 was worth +0.0091, from 0.9616 to 0.9707.

The reason is structural. Once every stated constraint is matched, dozens of products tie exactly, because the constraints are low-entropy strings like Imported or 100% Polyester that hundreds of products share. At that moment popularity is not a tiebreak of convenience — it is the only route still carrying information about which of the tied candidates is the answer.

Reversal 02 · the exactness step

A well-argued fix that lost in 8 of 8 configurations

One session was missed, so we added a bonus for candidates matching every constraint exactly, reasoning that full coverage is qualitatively different from near coverage. It scored worse everywhere and did not fix the session. Diagnosis afterwards: that target already matched all four constraints and was the most-reviewed of the twenty products that did. It was never a coverage problem — it was the tie-break, which is Reversal 01. The code is gone; the finding stayed.

Reversal 03 · the tuning trap

Tuning on the clean score quietly wrecked the insurance number

The weights that maximised the clean score assumed exact matching works. With the spec route switched off, those same weights scored 0.7442 — barely above the do-nothing popularity floor — because a dominant popularity weight swamped the two routes that still had something to say.

The fix is the adaptive router: read whether exact matching is firing at all this turn, and switch weight profiles when it is not. That is 0.7442 → 0.8315, and it costs 0.005 of stressed score. It is also the first thing in this build that genuinely earns the brief's "runtime workflow re-orchestration" — the agent detects that a strategy has stopped working and changes strategy.

Two more results

Things that cost nothing, and things that cost nothing to skip

The offline dense backend is free. TF-IDF→SVD built from the catalog at startup scored 0.9707; bge-m3, with all 50,000 products embedded through the API, scored 0.9676. Statistically identical. The API path costs a per-turn network call, a 98 MB artifact and a live-endpoint dependency during official scoring, and buys nothing measurable. R2 ships with no network requirement at all.

The scheduled blend beats RRF decisively — 0.9707 against 0.8625 — confirming the project's earlier finding on a completely different pipeline. RRF throws away score magnitude, and popularity here is a strength signal, not merely an ordering.

The LLM stage

An 82% failure rate cost 0.0065

The brief names "Multi-Route Retrieval → LLM Semantic Ranking" as the required pipeline, so the stage is built: qwen3.6:35b, listwise over the top 20, called only as an escalation when the deterministic path is unsure. Measured, it scored 0.9642 — slightly worse than leaving it out.

That measurement is not clean, and saying so is the point. A second session on this machine was working the R1 road against the same shared endpoint and saturating its rate limit: 318 of 386 calls returned HTTP 429. A direct probe confirmed the endpoint refuses after two requests. The reranker's own merits are therefore unmeasured.

But the run established something better than it set out to. With more than four in five model calls failing, the agent lost 0.0065. That is the escalation-only design behaving exactly as designed — the model is consulted only when the deterministic ranking is unsure, and a failed call returns the original order untouched. The LLM is a bonus, never a dependency. "What happens if the endpoint is down during official scoring" is now a measured answer rather than a hopeful one.

It also vindicated the instrumentation. The project has already recorded one occasion where 60 silently-failed calls were scored as "the model doesn't help" — a confidently wrong conclusion that survived for days. Here every call site asserts on a parsed non-empty result and counts failures, so the contention was visible in the same line as the score.

Honest limits

What this does not prove

The stress rewriter is rule-based and deliberately harsher than anything the organizer is likely to ship — token reordering, synonym substitution and case changes inside the constraint strings. It is a lower bound on robustness, not a prediction, and R2's advantage under it is a claim about shape of failure, not a forecast of the private-set score.

The weight schedule was tuned on 200 sessions. The optimum is a broad plateau rather than a peak, which is evidence against a knife-edge fit, but it is still 200 sessions. And the two robustness conditions pull in opposite directions: the profile was chosen on best worst-case, which costs about 0.01 against optimising for either one alone.

Finally, R2 still leans on inversion for its clean score. The honest way to report this build is both numbers together — 0.9707 with the spec-phrase route and 0.8315 without it.
